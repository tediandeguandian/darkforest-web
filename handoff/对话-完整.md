## A 款｜《三体 黑暗森林·桌游》（游歌桌游）—— 隐藏坐标博弈

这是最贴"黑暗森林法则"原著的一款，民间设计被官方认可，**限量约 300 套**，二手已溢价。

**核心设定**：每人代表一个文明，随机抽 1–9 号星系牌作坐标，**对全场保密**。目标就一句原著台词——**"藏好自己，做好清理"**。谁活到最后谁赢，也可能全场无赢家。

**回合流程（三段式）**：
1. **生产** — 默认 +1 能量，建设区有生产设施则额外产出
2. **行动** — 二选一：打出任意张牌 **或** 弃置任意张牌
3. **补给** — 手牌补至 4 张，交给下家

这个"出牌 vs 弃牌"二选一就是节奏阀门：**出牌必然泄露信息，弃牌等于沉默**。

**三类手牌**：

| 类型 | 机制 |
|---|---|
| **广播牌** | 双面（合作/伪装），背面朝上打出，指定距离内的星系。恒星广播(0能量/距离1)、宇宙广播(1/2)、超距广播(2/2) |
| **建设牌** | 一次性花能量，之后每回合持续产出（主要是生产设施） |
| **打击牌** | 只针对坐标不针对玩家，**延时生效** |

**广播结算（囚徒困境）**：双合作各 +3；一合作一伪装，伪装方 +5、合作方 0；双伪装各 0；无人回应发布者 +1。单看收益"伪装"永远不吃亏——**但回应本身就在泄露你的位置**，广播距离就是半径，回应即等于承认"我在这个圈内"。

**打击牌（本作最贴题的机制）**：科技锁死（立即生效，废掉对手所有建设牌）→ 热核打击 → 光粒打击（无视防御毁灭恒星）→ 湮灭打击（毁灭恒星+所有建设）→ 降维打击（彻底清除星系，约 10 能量）。打出后按**距离**每回合放 1 个进度指示物，攒够才生效。所以全场知道你打了谁，但**不知道什么时候到**——这段飞行时间就是信息战窗口。命中后打击者获得 **(剩余玩家数 × 3)** 点能量，且**被淘汰者已发出的打击牌仍会继续结算**，死人也会开枪。

## B 款｜《我的三体：黑暗森林》（官方授权 / 卡卡士多 × Asmodee）—— 舰船竞速

## 二、系统架构（房间制）

```
大厅服务 ──┬── 认证 / 好友 / 排行（无状态）
          └── 对局服务（有状态，Sticky Session）
                ├── RoomManager：创建/加入/踢人/房主移交
                ├── GameEngine：状态机 + 指令 reducer（核心）
                ├── VisibilityFilter：按玩家裁剪下发数据
                └── ReplayService：全量指令日志流
```

**关键约束**：`GameEngine` 是唯一真相源，所有合法性校验（手牌、距离、能量、时序）都在服务端完成，前端只发**意图**不发言结果。

这个设计思路很干净——**把"难度"完全绑定在记忆保真度上**，AI 与真人信息对等，规则零改动，难度差异自然从推理质量里长出来。下面是完整设计大纲。

## 一、难度命名与参数

三体里恰好有一条完美的隐喻链：**三体人的记忆会随脱水/环境而改变**。

| 难度 | 名称 | 记忆保留率 | 有效记忆窗口 | 状态 |
|---|---|---|---|---|
| 低 | **脱水者** | ~25% | 约最近 1 个回合 | 醒来就忘，丢三落四 |
| 中 | **乱纪元** | ~50% | 约最近 2–3 个回合，随机断片 | 记忆时长短、断续 |
| 高 | **恒纪元** | ~85% | 最近 5–6 个回合，偶有遗漏 | 稳定规律，接近完整 |
| 地狱 | **智子** | 100% | 全量事件 | 全知观察者 |

> 智子的设定还额外自洽：它**能看到地球上发生的一切，但读不到人的思想**——正好对应"AI 知道所有已发生的公开事件，但不知道任何人手里的牌"。

---

## 二、公平性红线（AI 绝对不能知道的事）

这是整个设计的地基，必须写成断言层（开发模式下每次 AI 取数都跑一次 `assertNoHiddenAccess()`）：

| 禁止获取 | 说明 |
|---|---|
| 其他人的真实星系坐标 | 只能靠推理得到概率分布 |
| 其他人的手牌 | 包括"他没打什么牌"也不能当已知条件 |
| 其他人的出牌意图 | 谈判频道的发言一律视为**不可验证声明**，需打折处理 |
| 未来的抽牌 | 与真人完全一致 |

**关键形式化**：「别人没回应广播」**不等于**「别人不在这个星系」。必须按贝叶斯处理：

```
P(玩家o在星系g | 对g的广播无人回应)
  ∝ P(无人回应 | o在g) × P(o在g)
其中 P(无人回应 | o在g) = P(o手里没有广播牌)   ← 用手牌供给历史估先验
      P(无人回应 | o不在g) = 1
```

低难度 AI 恰恰容易在这里犯错（把"没回应"当成"不在"），而这**不需要额外写代码**——它只是记忆残缺导致的后验算错，天然产生。

## 三、信息模型：AI 的"感官"

AI 能观测到的公开事件流（与真人同桌看到的东西一一对应）：

| 事件 | 可见内容 | 是否泄露位置 |
|---|---|---|
| 广播发布 | 发布者、目标星系、广播类型与距离 | ✅ 强：`dist(发布者, 目标) ≤ d` |
| 广播回应 | 回应者身份、牌面（合作/伪装） | ✅ 强：`dist(回应者, 目标) ≤ d` |
| **超距广播** | 同上 | ❌ **无**（高维投影不暴露位置） |
| 打击宣布 | 打击者、目标星系、所需进度 | ✅ 强：进度需求 = 精确距离 |
| 打击生效 | 目标星系被毁 | ❌ 无 |
| 建设牌 | 正面放置在建设区 | ❌ 无（但产能可被观察） |
| 星系标记 | 黑/紫/红指示物 | ❌ 无（**版图状态，永不遗忘**） |
| 能量变动 | 增量数值 | ⚠️ 弱：可反推行为类型 |

**版图状态永不遗忘**——标记是摆在桌上的实物，所有人一直看得见。这条要写进架构，否则"脱水者"会站在被二向箔清理过的星系上，显得像 bug。

## 四、记忆系统实现

```ts
type PublicEvent = {
  id: string; round: number; type: EventType;
  actor?: string; targetGalaxy?: number; distance?: number;
  outcome?: 'cooperate' | 'disguise' | 'none'; revealed: boolean;
};

// 每个 AI 持有一份独立的 EventStore
class MemoryStore {
  events: PublicEvent[] = [];      // 观测到的原始流（全量，仅用于调试）
  retained: PublicEvent[] = [];    // 该难度实际"记得"的子集

  retain(level: Difficulty, age: number): boolean {
    const base = LEVEL.baseRate[level];          // 0.25 / 0.5 / 0.85 / 1.0
    const tau  = LEVEL.decayTau[level];          // 越难 tau 越大（记更久）
    return Math.random() < base * Math.exp(-age / tau);
  }
}
```

设计要点：

1. **遗忘 = 采样掩码**，只删信息不造信息。随年龄指数衰减，模拟"人更记得最近发生的事"。
2. **记忆在游戏开始时一次性决定保留与否**，中途不再翻转（避免 AI 行为前后矛盾）。
3. **用固定 seed**，保证同一难度可复现，便于回归测试。
4. 保留率只影响 `retained`，**推理引擎与决策策略对所有难度完全相同**——这是"规则不变"的硬承诺。

## 五、推理引擎（四难度共用）

**信念矩阵**：对每个对手 o、每个星系 g，维护 `P(o 在 g)`，初始均摊 1/9。

每收到一个保留的事件，做一次似然更新：

```
发布者X 对 T 发起距离 d 的广播  →  P(X在g) ∝ 𝟙[dist(g,T) ≤ d]
玩家Y 回应了该广播            →  P(Y在g) ∝ 𝟙[dist(g,T) ≤ d]
超距广播的回应                →  似然 = 1（零信息量，需特殊处理）
X 对 T 的打击需要进度 k       →  P(X在g) ∝ 𝟙[dist(g,T) = k]   ← 精确距离，信息量最大
```

**三角定位**：多轮观测的距离约束会自然收敛，`智子` 因为记得全量，往往第 2–3 轮就能把某人的位置锁到 2–3 个星系内；`脱水者` 只有最近一两轮约束，矩阵接近均匀，只能瞎猜。

**策略用的量**：
- `entropy(P)` → 广播目标选择：打哪个星系能让全场信念熵下降最多（信息增益最大化）
- `threat(o) = P(o在g) × 战力(o)` → 打击目标选择

## 六、决策策略（共用，不随难度变）

| 阶段 | 策略 |
|---|---|
| 生产/补给 | 自动执行，无决策 |
| 出牌 or 弃牌 | 手牌利用率低于阈值时弃牌囤资源；否则出牌 |

## 实现（伪代码）

```ts
// 每回合结束时调用一次
function endRound(ai: AI, newEvents: PublicEvent[]) {
  const E = [...ai.memory.pool, ...newEvents];   // 全量总和
  const M = [...ai.memory.retained, ...newEvents]; // 先全部纳入候选

  const target = Math.round(LEVEL.retention[ai.level] * E.length);

  while (M.length > target) {
    const i = Math.floor(Math.random() * ai.rng());  // 固定 seed，可复现
    M.splice(i, 1);                                   // 无放回均匀随机移除
  }

  ai.memory.pool = E;
  ai.memory.retained = M;
}
```

三条设计约束：

1. **单向收缩**：一条记忆一旦被抹掉就永不回来（因为新事件只有本回合这四条），避免 AI 行为前后矛盾。
2. **固定 seed**：`rng` 用该 AI 的 seed 初始化，保证同难度可复现、可回归测试。
3. **保留率只作用于 `retained`**，推理引擎和决策策略对所有难度跑的是同一份代码。

## 最终记忆模型

```
可见信息 = 本回合实时事件流（直播，不过滤）+ M（记忆池）

M 的构成：
  ├─ 上一回合的全部事件      ← 硬保护，100% 永不抹除
  └─ 更早回合的事件随机幸存   ← 从"总和"里按难度随机删
```

**"回合"的定义**：所有玩家各行动一次为一个回合（对应规则书里"所有玩家行动完毕后，进入下一回合"）。AI 在自己回合内做决策时，"上一回合" = 上一个完整回合。

本回合已经发生的事不走记忆池，直接走实时流——所以 AI 永远不会出现"忘了五分钟前发生的事"这种明显 bug。

## 实现（严格单向收缩）

```ts
// 每个回合结束时调用一次
function endRound(ai: AI, thisRoundEvents: PublicEvent[]) {
  const E      = [...ai.memory.pool, ...thisRoundEvents];  // 全量总和，只增不减
  const older  = E.filter(e => e.round < currentRound);     // 上一回合之外的全部历史
  const target = Math.round(LEVEL.retention[ai.level] * E.length);

  // 上一回合硬保护
  const protectedNow = thisRoundEvents;

  // 旧记忆只减不增：已记住的旧事件优先留下，超出容量才随机抹
  const keptOlder = ai.memory.retained.filter(e => e.round < currentRound);

  const over = (keptOlder.length + protectedNow.length) - target;
  if (over > 0) {
    const n = Math.min(over, keptOlder.length);
    for (let i = 0; i < n; i++) {
      keptOlder.splice(Math.floor(Math.random() * ai.rng()), 1);  // 无放回均匀随机
    }
  }

  ai.memory.pool     = E;
  ai.memory.retained = [...keptOlder, ...protectedNow];
}
```

四条硬约束：

1. **保护优先于保留率**。若 `|上一回合| > target`（极端情况：某回合事件特别多），宁可超出容量也绝不删上一回合的牌。
2. **单向收缩**。旧记忆一旦被抹就永不回来——因为新事件只有本回合这几条，被删的旧事件不可能重新入池。避免 AI 行为前后矛盾。
3. **固定 seed**。`ai.rng()` 用该 AI 的 seed 初始化，同难度可复现、可回归。
4. **只作用于 `retained`**。推理引擎与决策策略四难度共用同一份代码，零分支。

## 机制本身（设计 MD 新增 2.5 节）

- **公共弃牌堆**，全场共用一个，所有人弃掉/打完的牌都进这里，**对全员公开**（不做可见性裁剪）
- **可查看范围 = 本回合实时 + 上一回合**，信息**保质期 2 个回合**；更早的已洗回牌库，谁也查不到
- **每位玩家回合结束时**滚动一次：上一回合弃牌洗回牌库 → 本回合弃牌成为新的"上一回合区" → 本回合区清空
- **无洗牌动画**，列表直接清空 + 一行日志"N 张牌已洗回牌库"
- 按你的定义：**一回合 = 一位玩家的回合**，且包括其他人在这一回合内出的牌（回应广播的牌、被科技锁死逼弃的建造牌等）

## 一个意外的收获：它让记忆模型彻底自洽

你这条机制最大的价值不在信息量，而在于**给"上一回合"装上了物理对应物**：

> 记忆模型里"上一回合硬保护 100% 记住"此前只是模拟健忘的**假设**；现在它正好对应"上一回合的牌还能在弃牌堆里翻到"这一**事实**。

由此得到一条干净的公平性辩护：**四个难度 = 四档"记笔记的勤奋程度"**——智子是逐条记录、过目不忘的真人（规则不禁记笔记，所以不是作弊），脱水者只看得见眼前弃牌堆。每个难度记住的都是曾公开过的信息。

前提是两者**共用同一个 `turnIndex`**——这也是我把"回合"显式重定义的原因。

## 连带改动（不止加了一节）

1. **术语重定义**：「回合 turn」＝一位玩家的回合，「轮 round」＝一圈（规则书原话）。记忆模型伪代码里的 `round` 全部改为 `turn`，避免与新术语冲突
2. **实战影响三条**：弃牌不再是沉默（弃什么会被看一回合）；科技锁死会泄密（逼弃的建造牌公开晾出来，等于替全场调查目标）；被淘汰者手牌公开一回合
3. **数据模型**：新增 `DiscardPile{current, last}` 与 `DiscardedCard{cardId,name,type,ownerId,turn}`；`PublicEvent` 加 `discard`、`deck_reshuffle` 两个事件类型

## 最重要的技术影响：AI 推理结构升级（4.5 节新增）

信念矩阵从"每格独立"变成受约束的矩阵：

```
每个星系最多一个玩家：  Σ_o P(o 在 g) ≤ 1
每个玩家恰在一个星系：  Σ_g P(o 在 g) = 1
```

**收敛速度会显著变快**：一旦某人被锁到星系 g，其余所有人立刻从 g 排除——一次确定，全场受益。

实现上用**全局一致性投影**：

| 方案 | 算法 | 用途 |
|---|---|---|
| A | Sinkhorn / 迭代比例拟合 | 每回合常驻更新，开销可忽略 |
| B | 匈牙利 / 最小费用流 | 选打击目标前跑一次，求精确一一对应 |

而且约束是**动态的**：有人被淘汰 → 其星系空出、列容量释放；有人跃迁迁入 → 重新占用。每次淘汰/跃迁后都要重跑投影。

**对四难度的意义**：投影模块四难度共用、零分支，但输入质量因记忆残缺而不同——智子的矩阵投影后往往直接得唯一解；脱水者的约束太少，投影出来依然一片模糊。**难度曲线会因此更陡，而且仍然不需要 `if (level === ...)`。**

## 为什么 KV 不行

| 问题 | 后果 |
|---|---|
| **最终一致**（写入到全局可见有延迟，可能数十秒） | A 玩家出完牌，B 刷新看到的还是旧状态 |
| **无原子操作/事务** | 两个玩家同时响应广播 → 后写覆盖先写，直接丢操作 |
| **不能保持长连接** | KV 只是存储，WebSocket 无处可挂 |
| **读延迟**（冷读需回源） | 每回合都要读全量状态，体验差 |

KV 适合存**只读/低频**的东西：房间索引、玩家 token、战绩。**不适合**做对局状态。

## 正确架构：Durable Objects 做房间，KV 做边缘数据

```
Worker（路由 + 静态资源）
   ├─ /api/create        → 生成房号，建 DO 实例
   ├─ /ws?room=ABC       → 转发给该房间的 DO
   └─ 静态资源            → Assets

Durable Object「Room ABC」（单实例、单线程、强一致）
   ├─ 持有 game 状态 + 所有 WebSocket
   ├─ SQLite 持久化（Hibernation 唤醒后可恢复）
   └─ 广播按人裁剪的 view

KV（可选）
   ├─ room:{id} → 房间元信息（用于大厅列表）
```

## ⚠️ 对局状态不能放 KV

| 需求 | KV | Durable Object |
|---|---|---|
| 强一致 | ❌ 最终一致，写入到全局可见有延迟 | ✅ 单实例单线程 |
| 并发写不丢 | ❌ 无事务，后写覆盖先写 | ✅ 天然排队 |
| WebSocket 长连接 | ❌ 无法保持 | ✅ Hibernation |
| 每房间独立状态 | ❌ 靠 key 拼 | ✅ 一房间一实例 |

具体到你的游戏：两个玩家同时提交广播响应，KV 会**丢一个**——这不是性能问题，是正确性问题。

**一句话：KV 是缓存，DO 是房间。**

**记忆的落地方式比设计稿更干净**：不做"每回合随机删几条"，而是**确定性抽样**——

```js
// 上一回合硬保护；更早的事件按保留率抽样，用 event.id + seed 做哈希
keep = e.turn >= turnIndex - 1 || hash01(e.id * 2654435761 + seed) < retention
```

好处是记忆变成 `(事件流, 难度, seed)` 的纯函数：**不用存档**、DO 休眠唤醒不丢、重启不丢，而且同一个事件要么永远记得要么永远忘了，不会"时好时坏"。固定 seed 可完整回放。

**推理**用约束集合而非贝叶斯矩阵：广播泄露"我在目标 d 以内"、打击泄露"我距目标正好 k 跳"、跃迁落点直接公开，再叠加"一个星系只容一人"的互斥传播。约束互相矛盾时退化为全图均匀——**宁可不知道，也不能自信地错**。

## 1. 没广播牌 = 无法回应

## 2. 广播必须等待

| 情形 | 等待 | 到点后 |
|---|---|---|
| 至少一人能回应 | **60 秒** | 未响应的强制者自动出牌（优先伪装面），其余视为不回应 |
| 没人能回应 | **随机 5–20 秒** | 自动结算：发布者 +1 能量 |
| 多人响应、发布者不挑选 | **15 秒** | 自动按"合作优先"结算一名 |

- **引擎**：`tickBroadcast(now)` 统一处理超时；`playBroadcast` 不再立即结算
- **Node**：700ms 轮询活跃房间
- **Cloudflare**：Durable Object 的 `alarm`，到点唤醒（休眠也会醒）
- **AI 自走模拟**：跳过这段空等，避免测试卡住

## 能量飘字

任何人能量变动时，其能量数字旁浮出 `+3`（青色实心块）或 `−6`（红色实心块），**约 3 秒可见，随后 0.6 秒淡出**，边淡边向上飘 26px。

覆盖**全部六种**能量变动来源：

| 来源 | 显示 |
|---|---|
| 生产阶段 | `+1` 或 `+3`（含产能件加成） |
| 建造 | `−2` / `−6` / `−8`… |
| 广播结算 | 发布者净变化、响应者 `+3` / `+5` |
| 发射打击 | `−4` ~ `−10` |
| 清场奖励 | `+9` / `+15`… |
| 光速飞船 | `−N`（清空全部能量） |

**一个刻意的处理**：广播是"发布时不扣费、结算时才扣"，如果照实拆成 `−1` 和 `+3` 两条飘字会互相打架。所以引擎按**净变化**只发一条（`-1+3 → +2`），视觉上干净，语义上也符合"一次结算"。

实现上事件是服务端权威产出的（`energy` 事件带 `actor / delta / reason / total`），不是前端 diff：
- **不会漏**：连续多次变化各自成一帧，靠事件 id 递增判重
- **不会重复飘**：首屏/重连时只记游标，不补飘历史
- **不随重渲染丢失**：飘字挂在独立 fixed 层，`renderGame` 重建 DOM 也不影响

## 三处需要你确认的判断

**① 被选中的回应者也要付费。** 你说"未被选中者消耗卡牌能量后返还 1 点"——如果被选中者免费出牌，那句"返还"就没有对应的扣费基准了。所以我统一成"打出的广播牌都要付自己的费用"，只有未选中者退 1 点。连带效果：**用 2 费的超距广播回应合作广播，净收益是 +3−2 = +1**，不再是白赚。

**② 打击距离的连带后果比预想大。** 隐藏轮数等于砍掉 AI 最强的定位信号（原来"进度=k"就是精确距离）。我给它补了一条补偿规则：**打击落空/命中也告诉全场"这个星系那时有没有人"**，AI 能据此排除。修完难度曲线恢复正常（对局 35 回合左右，不再是 240 回合热寂），但智子对脱水者的优势从 39:21 降到约 **54:46**——记忆的价值被这条规则削弱了，属于规则本身的必然结果。

**③ 同一回合的第二个动作只等 1–2 秒。** 一个 AI 回合常有两三个动作（广播→结束），每个都等 5–10 秒会让 9 人局一盘等十几分钟。所以只有"轮到他"的第一下等 5–10 秒。

### 1. 光速飞船改成「挨打时手动决定」

原来的实现有两个问题：它是一张能被主动**建造**的建设牌，而且打击命中时会**自动**帮玩家跃迁——等于替玩家做决定。现在改成：

|---|---|
| 平时 | **不能建造**（`playBuild` 直接拒绝，提示「只能在遭到打击时启动」），卡片以「应急 / 仅挨打时」样式留在手牌，点它会被拦住 |
| 触发 | 只在这一击**会要命**（没有防御牌能挡）、手里有牌、能量 ≥ 10、本局没用过时，才挂起询问 |
| 选择 | 弹出「启动光速飞船 / 放弃」，**30 秒不选视为放弃** |
| 启动 | 弃掉这张牌 + 弃全部建设牌 + 能量归零 + 随机空星系（落点仍不公开） |

人机遇到这个抉择一律选择「跑」。

改动过程中还发现一个严重问题：同一回合有两枚打击同时到期时，第一枚挂起后第二枚会覆盖挂起状态，把 `step` 留在 `escape` 上，整局卡死且没有任何报错——全 AI 模拟里表现为「跑满 3000 步还打不完」。已改成一旦挂起就暂停后续打击结算、`prevStep` 不再继承 `escape`。修复后连跑 40 局全 AI，40 局全部正常收局。

### 2. APK 退出键失效

根因不是按钮没绑事件，而是 **Android WebView 默认不实现 `window.confirm`**，调用会直接返回 `false`。代码是 `if (confirm('确定退出当前对局？')) { ... }`，于是永远走不进去——点了没反应。

修复：在 `MainActivity` 注册 `WebChromeClient`，把 `alert` / `confirm` 用原生 `AlertDialog` 接管。这样不光是退出键，页面上其它所有确认框在 APK 里都恢复可用。浏览器里也复测了完整流程：点退出 → 确认 → 回到入口页。

### 3. 广播回应不等满 60 秒

60 秒是**上限**。规则引擎本来就支持「全员表态即结算」，但**离线版和局域网版的代码路径没有触发结算**——玩家回应后只提交了 response，没有人调用 `finalizeBroadcast`，只能干等 60 秒超时。联机版（Node / Worker）因为服务端有这一步，所以是对的。

修复：在 `local.js` 加了 `applyAndSettle()`，回应一旦 `complete` 就立刻结算，本地动作和局域网转发过来的动作两条路径都走它。

顺带删掉了一个早就失效的倒计时函数——它引用了未定义的 `v`，只是因为在弹窗里找不到 `#respTimer` 元素而提前 return 才没报错。

## 382. 用户

自己给自己打击后会卡住，房间直接卡死，被自己打击的玩家会一直处于出牌阶段。

## 383. 助手

## 已经修好了，原因很直接

**触发条件**：朝自己所在星系开火（距离 0），并且自己没有防御牌、也没有可用的光速飞船。

**为什么会卡住整个房间**：

```js
if (d === 0 || def.immediate) resolveStrike(st);   // 立即结算，把自己打死了
return { ok: true };                                // ← 然后什么都没有了
```

`resolveStrike` 里的 `eliminate()` 只是把 `alive` 置为 `false`，**没有任何人推进回合**——`S.currentIdx` 仍然停在这个刚被淘汰的玩家身上，`step` 也仍然是 `action`。

而前端在 `canAct` 里检查了 `me.alive`，已出局的玩家看不到「不出」「提示」「出牌」「弃置」中的任何一个按钮，只会显示“你已出局，可继续观战”。结果就是：**当前席位是一个既不会行动、也不会被跳过的人**，整局就停在那里了。

顺带说明一下，为什么 `endTurn` 在这里帮不上忙：它当时只检查“是不是你的回合”，不检查你是否还活着。因此服务端虽然接受 `endTurn`，但界面上根本没有按钮可点。

## 修法

1. **新增 `advanceIfCurrentDead()`**：当前席位的人已经出局时，直接调用 `nextPlayer()`。在“距离 0 或立即生效”的打击结算完之后调用一次：

```js
if (d === 0 || def.immediate) {
  resolveStrike(st);
  advanceIfCurrentDead();   // 打的是自己脚下，可能把自己打死
}
```

这个问题要分两种玩法回答 —— 因为**离线版和局域网版完全不经过服务器，玩多少局都不消耗额度**。

## 结论先行

| 玩法 | 每天能玩多少 | 限制来自 |
|---|---|---|
| **离线（本机人机）** | **无限** | 手机自己算，跟服务器无关 |
| **局域网（手机当主机）** | **无限** | 只走你家的 Wi-Fi |
| **在线 · 纯真人局** | **约 800 局/天** | Cloudflare DO 请求额度 |
| **在线 · 1 人 + 2 人机** | **约 300 局/天** | **Durable Object 行写入**（AI 每思考一步都要存一次快照） |

## 依据

Cloudflare Workers 免费计划对 Durable Object 的每日额度（官方定价页）：

| 维度 | 免费额度 | 我们怎么用 |
|---|---|---|
| 请求 | 100,000 / 天 | 每次 alarm 唤醒 = 1 次；**入站 WebSocket 消息按 20:1 折算**（100 条消息只算 5 次） |
| 行写入 | 100,000 / 天 | 每步存快照 + 每次 `setAlarm` 各 1 行 |
| 计算时长 | 13,000 GB-s / 天 | 有 Hibernation，闲置不计时，基本用不完 |
| 存储 | 5 GB | 每局快照几十 KB，远远不够用 |

一局 40 回合、1 真人 + 2 人机的实际消耗（测算）：

- AI 步数 ≈ 2 × 40 × 1.5 ≈ **120 次 alarm** → 120 个请求
- 真人 60 条操作 → 折算 **3 个请求**（20:1）
- 快照 + alarm 写入 ≈ **300 行**

瓶颈是 **行写入 10 万/天 ÷ 300 ≈ 333 局**，请求那边还很宽裕。

## 几个降低额度的办法

1. **人机局别开太多 AI** —— 每多一个 AI，几乎线性增加 alarm 和行写入。2 个 AI 的局比纯人对局贵一个数量级。
2. **观战时把手机屏幕关掉** —— 连接会断，DO 进入 Hibernation，不再计计算时长。
3. **想连开几局，用离线/局域网** —— 完全零消耗，而且延迟比走公网低。
4. 真要办活动（比如十几个人同时在线），$5/月的 Workers Paid 就有 100 万请求 + 5000 万行写入，量级差 1000 倍。

## 一个提醒

免费额度是按 **UTC 零点** 重置的（北京时间早上 8 点）。超了不会扣钱，而是**该类型操作直接报错**——表现为“创建房间失败”或“对局卡住不动”，很容易被误认为 bug。如果哪天真遇到这种情况，先想到额度，而不是代码。

按现在这个玩法（一天两三局），免费额度大概能用十几年。

## 387. 助手

免费额度本身没有上限，但有两类不同性质的限制，需要分开说明。

## 一、按天重置的“消耗型”额度 —— 没有总额上限

| 维度 | 免费额度 | 重置方式 |
|---|---|---|
| 请求（含 WebSocket 消息、alarm） | 100,000 / 天 | 每天 UTC 0 点（北京时间早 8 点）清零 |
| SQL 行写入 | 100,000 / 天 | 同上 |
| SQL 行读取 | 5,000,000 / 天 | 同上 |
| 计算时长 | 13,000 GB-s / 天 | 同上 |

这四项都属于**每天重新发放**的额度：今天用完明天又有，一年 365 天都如此，不存在“账户总共只有 100 万次”这种累计上限。所以“还能玩多少局”每天都会重新计算。

## 二、按占用计算的“存储型”额度 —— 这个是累计的，不清零

| 维度 | 免费额度 | 性质 |
|---|---|---|
| 存储总量 | **5 GB** | 你放多少数据就占多少，不随时间重置 |
| Durable Object 数量 | 不限 | 按房间创建，空房间会被回收 |
| DO 单对象存储 | 10 GB | 远达不到 |

我们是每个房间存一份游戏快照（几十 KB），对局结束后房间过期即被清理，5 GB 基本用不到 0.01%。**这一项才是真正“不重置”的**，但它离我们很远。

## 三、超额之后会怎样

免费计划**不支持“超一点付一点”**。任一维度超额后：

- 该类型的操作会**直接报错**，直到下一个 UTC 零点重置
- 表现是“创建房间失败”“对局卡住不动”，不像账单提醒
- **不会自动扣费**——没绑卡不可能扣钱，绑了卡只要不手动升级 Paid 也不会扣

想解除限制只有一条路：手动升级 Workers Paid（$5/月起，100 万请求 + 5000 万行写入/月）。

## 四、一个容易踩的点

如果以后给房间加 **KV 索引**（`env.META`），KV 免费额度里**写入只有 1,000 次/天**——比 DO 的 10 万行写入窄两个数量级。现在 `wrangler.toml` 里没绑 KV，所以没这个问题；哪天要加，记得别在每次动作时都写 KV。

**结论**：消耗型额度每天刷新，没有累计上限；唯一不重置的是 5 GB 存储，而我们用不到千分之一。照现在一天两三局的玩法，这个免费额度实际上等同于“无限”。

### 快速对局到底改了什么

| | 标准 | 快速 |
|---|---|---|
| 出牌后还能弃牌吗 | 能 | **不能**（`discardUsed` 在出牌时就置真） |
| 弃牌之后 | 补满 4 张，还能继续出牌 | **直接结束回合**，交棒给下一位 |

实现上就三处：

```js
// 出牌即封住弃牌
function markActed() {
  S.actionCount++;
  if (S.mode === 'fast') S.discardUsed = true;
}

// 弃牌即交棒
if (S.mode === 'fast') { endTurn(p.id); return { ok: true, endedTurn: true }; }

// 回合开始不补
if (S.mode !== 'fast') refillHand(p, '回合开始补牌');
```

## 生成后的自检（这四条不过就重做）

1. **有没有蹦出文字或数字**——AI 特别爱在圆环上塞刻度数字，一旦出现就废。
2. **主体是否真的居中**——很多模型会把整体偏下 5–10%，后面裁自适应图标时会被切掉。
3. **缩到 48×48 看一眼**——如果这时只剩一团糊，说明元素太碎，要求“simpler, fewer elements, larger shapes”重生成。
4. **环的缺口方向**——提示词要求右上缺口，生成成别处也能用，但四张里挑缺口在右上、红刻度在左上那张（构图更平衡）。
